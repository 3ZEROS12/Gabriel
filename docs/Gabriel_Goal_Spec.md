# Gabriel — Goal Spec（供 Agent Goal 模式使用）

> 本文档定义 Gabriel 项目的目标终态与可验证的完成标准，供自主 Agent 在 Goal 模式下持续迭代时作为对齐依据。每完成一项，应对照"验收标准"自检，而不是凭主观判断"感觉做完了"。

---

## 0. 一句话愿景（North Star）

Gabriel 应该成为**重度 CLI Agent 用户会下意识依赖的旁路控制台**——一个开发者卡在主 Agent 任务里、想问岔路问题或回顾过去经验时，第一反应会打开的工具，而不是装了看一眼就卸载的玩具。

**成功不等于商业化，成功等于"有人离不开它"。**

---

## 1. 终态验收标准（Definition of Done）

以下四条全部达成，视为项目进入"成熟期"，可以停止大规模功能扩张，转入维护 + 精细打磨阶段：

- [ ] **多 Agent 覆盖**：至少 3 个主流 CLI Agent（Antigravity、Claude Code、Cursor 中至少三选三，或替换为实际用户占比最高的三个）拥有**完整、非降级**的日志解析体验（对照第 2 节验收标准）
- [ ] **知识库主动价值**：系统能在检测到用户遇到与历史记录相似的问题时，**主动**提示相关历史方案，而非仅被动响应搜索请求
- [ ] **真实使用信号**：至少 5 个非团队成员的真实用户，连续两周内每周实际打开使用 Gabriel（不是安装后闲置）
- [ ] **稳定性达标**：核心链路（日志 tailing、WebSocket 推送、对话流式响应）在连续 72 小时本地运行下无崩溃、无内存泄漏、无端口/进程残留

---

## 2. 功能分层与优先级（Agent 应严格按此顺序推进，禁止跳跃并行）

### P0 — 必须先完成，其余全部阻塞

**2.1 Claude Code 解析器补全**
- 现状：`ClaudeCodeParser.parse()` 是 stub，等同纯文本降级
- 目标：达到与 `AntigravityParser` 同等质量——正确区分用户输入/Agent响应/工具调用三类角色，正确截断与格式化
- 验收标准：
  - [x] 输入真实 Claude Code 日志样本，输出的 HTML 片段角色分类准确率 100%（人工抽查至少 20 条真实日志行）
  - [x] 异常/不完整 JSON 行不导致整体解析崩溃，有兜底处理
  - [x] 单元测试覆盖 `ClaudeCodeParser.parse()` 的正常、异常、边界（空内容、超长内容）三类输入

**2.2 第三个 Agent 解析器（Cursor 或团队实际使用率最高的工具）**
- 目标与验收标准同 2.1，替换目标 Agent 名称
- 前提：先确认目标用户群体实际使用哪个 Agent 最多，不要假设
- 验收标准：
  - [x] Cursor 日志解析完成
  - [x] 单元测试覆盖

### P1 — P0 完成后启动

**2.3 知识库关联能力**
- 现状：单纯的"总结 + FTS5 全文搜索"，纯被动
- 目标：新的日志上下文进来时，系统自动用 FTS5 检索知识库中语义/关键词相关的历史条目，若相似度超过阈值，**主动**在前端弹出提示（而非等用户手动搜索）
- 验收标准：
  - [ ] 有明确的"相关性判定"逻辑（可以先用关键词重合度做 v1，不必一开始上语义向量）
  - [ ] 前端有清晰的 UI 区分"主动推荐"与"用户主动搜索结果"
  - [ ] 误报率可控：人工测试 20 组场景，无关内容不应被错误推荐超过 10%

**2.4 真实用户验证循环**
- 这一项不是纯技术任务，Agent 负责的部分是：**提供便于收集反馈的机制**（如内置简单的"这个功能有用吗"反馈按钮、错误自动上报到本地日志文件方便复盘）
- 验收标准：
  - [ ] 用户能在不打断使用流程的情况下一键反馈问题
  - [ ] 反馈数据本地留存，格式结构化，便于后续分析

### P2 — 仅在 P0、P1 均稳定后启动

**2.5 多 Agent 并发监控（"九宫格" Mission Control）**
- 验收标准：
  - [ ] 支持同时展示 ≥2 个并发运行的 Agent session
  - [ ] 切换/聚焦某一 session 时不影响其他 session 的日志接收（无阻塞、无丢消息）

**2.6 一键安装分发（`pip install gabriel-ui`）**
- 前提：P0-P1 已验证稳定，不要在核心体验不稳时做分发，会造成负面口碑
- 验收标准：
  - [ ] 全新环境下一条命令安装成功率 100%（至少在 Windows/macOS/Linux 三个平台各测试一次全新环境）
  - [ ] 首次运行有清晰的引导流程，无需查文档就能跑起来

## 3. 明确的 Non-Goals（禁止在当前阶段做的事）

Agent 在 Goal 模式下容易"顺手"扩展范围，以下明确排除，除非未来单独立项：

- ❌ 前端框架迁移（React/Vue）——除非现有 Vanilla JS 已被证明是功能瓶颈，否则不做
- ❌ 企业级功能（RBAC、PII 脱敏、多租户 SaaS 控制台）——用户基数和验证阶段都不支持
- ❌ "个人数字分身"、生成式 UI 等远期构想——无明确验收标准的功能一律不进入本迭代
- ❌ GitHub 增长运营（爆款包装、动图制作）——产品未稳定前不做推广，会浪费第一波用户的信任
- ❌ 新增任何未在本文档列出的 P0-P2 功能，除非明确更新此文档

---

## 4. 技术护栏（避坑清单，Agent 必须遵守）

基于历史上已经踩过的坑，防止 Agent 在自主迭代时重蹈覆辙：

1. **禁止把主服务隐藏挂在后台任务里**——启动命令必须打印给用户，由用户在终端手动执行，不允许自作主张后台运行导致端口占用/孤儿进程
2. **禁止引入 pywebview 等原生桌面封装**——保持纯 Uvicorn Web 服务模式，如需桌面化只能用 Electron/Tauri，且需先立项评估
3. **禁止硬编码任何本机路径、用户名、密钥**——所有环境相关配置必须走 `config.json` 或环境变量
4. **禁止在 CSS 中使用 SCSS/Sass 专属语法**（如 `@extend`）——项目当前是纯 Vanilla CSS，没有预处理构建步骤
5. **所有新增 API 端点必须走 `verify_token` 依赖注入**，不允许绕过鉴权
6. **所有渲染到 `innerHTML` 的内容必须经过 DOMPurify（前端）或 `html.escape`（后端）处理**，无例外
7. **新增 Parser 必须继承 `BaseParser` 并注册进 `ParserRegistry`**，不允许在 `_scan_active_agents_sync` 或 `_format_transcript_sync` 里写 if-else 特判

---

## 5. 检查点节奏

建议每完成一个 P0/P1 子项，暂停并输出简短进度报告（对照第 2 节验收标准逐条自检），而不是闷头做完所有项再汇报——这样能尽早发现方向偏差，避免在错误方向上投入过多。

---

*本文档是当前阶段的快照，如果验证过程中发现某项目标不成立（比如目标用户实际最常用的 Agent 不是文档假设的那个），应更新此文档而不是绕过它继续执行。*
